# Motif 0.1.0 release plan

Motif 0.1.0 helps someone understand a saved FieldWorks project and take its parsing evidence into ChatGPT. The complete product is **Baseline → Assessment of that Baseline → Handoff of that Baseline and its Assessment**.

> **For agentic workers:** Use `subagent-driven-development` or `executing-plans` for implementation. This is the release work map and acceptance contract; settle the decisions below and write bounded implementation plans for the affected components before changing their contracts. Existing component plans are evidence, not authority to expand the release.

**Goal:** A linguist can install Motif, measure a saved project, inspect the findings, and give ChatGPT a self-contained, correctly matched Handoff without developer assistance or changing the FieldWorks project.

**Architecture:** Keep the shared command catalog, local Baseline and Assessment storage, and bounded PanGloss invocations. Bind viewing and export to an explicitly selected retained Assessment and its original Baseline. The Handoff is a local publication; the user uploads it to ChatGPT.

**Tech stack:** C#/.NET 10, Avalonia, LibLCM, SQLite, PanGloss, and the bundled standard-library Python reader where the ChatGPT upload route supports it.

**Status:** Implementation authorized; measured starting point is Motif main `faa9d93`. The execution ledger below records bounded work and verification; unchecked release exits remain outstanding.

**Review status:** Independent Sol architecture review approved the bounded retained-invocation storage/query slice. Export container and source-reference index qualification remain open before the public Handoff contract is frozen.

Two read-only Luna audits of the workflow and shipping code informed this map. Their concrete findings include lost Selection provenance, stale retry sources, incompatible capture/cleanup paths, developer-only parser discovery, and incomplete exported evidence.

## 1. Release boundary

The release has one purpose: help a person and ChatGPT inspect an existing project using actual parser evidence. Proposal authoring and project changes do not belong to the 0.1.0 user experience.

In scope:

- Choose a supported saved FieldWorks project, including one FieldWorks currently holds open.
- Capture the state as of FieldWorks' last save, including the writing-system data needed to interpret it.
- Select words, run a bounded Assessment, inspect completion, readings, approved-expectation comparisons, warnings, and timing.
- Reopen the retained result and export its matching Baseline and evidence.
- Give the resulting files to ChatGPT through a tested, documented upload path.
- Install, recover from ordinary errors, manage Motif-owned data, and obtain useful support.

Outside 0.1.0: Proposals, Trials, Dry Runs, apply, review/approval queues, Receipts, FieldWorks write integration, MCP, embedded chat, AI authentication/API keys, automatic upload, additional parser engines, broad grammar-authoring coverage, linked-media export, and collaboration/hosting. Existing implementation for future features can remain in source; the shipped 0.1.0 application and CLI must not expose Proposal or project-mutation functionality.

This scope supersedes Proposal-first release sequencing in the older roadmap. It does not erase the longer-term architecture or require unrelated engine code to be deleted.

## 2. Starting point and evidence

Much of the core workflow already runs. Release work must preserve that foundation while closing the gap between a developer demonstration and a dependable installed product.

| Area | Measured position | Remaining release obligation |
| --- | --- | --- |

| Baseline capture | Saved-file capture, scratch loading, lock/rename/truncation tests | Qualify supported project versions and concurrent saves in the release matrix |
| Assessment | Real parser, persisted evidence, limits, cancellation, approved morphology comparisons | Carry one explicit selected result through reopen, viewing, and export |

| Handoff | Atomic folder publication, grammar, Text exports, Selection, timing files, guidance | Reuse the selected Assessment; export the full analysis evidence and a verifiable file inventory |

Evidence: `docs/research/2026-09-15-motif-workflow-acceptance.md`, `docs/research/2026-09-09-native-window-workflow.md`, and `docs/superpowers/plans/2026-09-10-parse-morph-compatibility.md`. The app also builds a fresh Handoff request from its current Selection rather than identifying the displayed Assessment.

## 3. Planning assumptions and decisions

A small set of product choices determines the amount of shipping work. Windows x64 with bundled PanGloss is confirmed by the owner; the remaining defaults are planning assumptions until settled.

| Decision | Proposed default | When it must be settled |
| --- | --- | --- |
| Supported platform | **Confirmed: Windows x64.** Explicitly list supported Windows and FieldWorks project versions | Version matrix before packaging and qualification |
| Installation | **Confirmed: bundled PanGloss, no developer setup.** Include required runtime/native dependencies; no SDK, Rust, Git checkout, or local Python requirement | Package mechanics before the clean-machine prototype |
| Release version | **Confirmed: 0.1.0, not 1.0.** The first release is explicitly early; the 1.0 name is reserved for the release that carries Proposal authoring | Settled |
| CLI | **Confirmed: one artifact, one command vocabulary, gated by surface.** Every catalogued command declares `Released` or `Developer`; released help omits Developer verbs and released dispatch refuses them. `MOTIF_DEVELOPER_COMMANDS=1` re-enables them for development and tests. No build configuration switch, no second spelling of a verb, no deleted Proposal code | Settled |
| Released verb set | **Confirmed.** In: `open`, `analyses`, `config show`, `report`, `compare`, `baseline capture`, `assess`, `stats`, `handoff`, the corpus verbs, `baseline-refresh`, and every `jobs` verb. Out: all Proposal authoring and lifecycle verbs, `apply`, `dry-run`, `trial`, `log` | Settled |
| Meaning of Baseline in Handoff | AI-readable grammar, chosen Texts, source-reference index as needed, and provenance tied to the retained saved Baseline | Before file contract freeze |
| Raw source files | Do not upload the original `.fwdata`, writing-system directory, or database by default; decide separately if a raw Baseline attachment is a required user deliverable | Before file contract freeze |
| ChatGPT route | Manual upload to a tested ChatGPT web account with the required file/data-analysis capabilities; state the tested plan and limitations | Before export packaging is chosen |
| Handoff packaging | Test a compact upload package first; choose an archive only if ChatGPT actually reads it reliably, otherwise use a small supported structured/text file set | Before implementing the final export container |
| Project size/support | Qualify a small project, a representative working project, and a stress case; publish the measured envelope rather than promise every project size | Before release candidate |
| Signing/distribution | Named release publisher, downloadable versioned artifact, checksums and dependency notices; decide installer versus portable package and signing before publishing | Before release candidate |

An unsupported capability must have an explicit supported-scope statement and a clear refusal or limitation. A silently incomplete Baseline or mislabeled Assessment is not an acceptable scope reduction.

The files handed to ChatGPT must describe the result the user just inspected. Changing the project or Selection must never silently substitute different evidence.

- [ ] Specify selection of a retained invocation and its Assessment records using the existing identities; verify project, Baseline, Selection, scope, and invocation membership together.
- [ ] Persist the original Selection descriptor alongside final words/hash: chosen Text IDs, pasted input, all-wordforms choice, retry source Assessment and threshold. Current source/count summaries do not preserve that request. Distinguish two requests that yield identical words.
- [ ] Add a retained-run query grouped by invocation; do not infer the selected run from the newest row of one Assessment kind or reuse a Proposal-oriented current pointer without defining its release semantics.
- [ ] Make Handoff export that selected result. Remove implicit Assessment reruns and current-Selection recomposition from the export path.
- [ ] Capture or retain all source/export artifacts needed later while the measured Baseline is available. Export must not depend on the live project still having the old content.
- [ ] Reopen the last retained result after app restart; allow an explicit result choice where multiple eligible runs exist. A simple chooser is sufficient; no general history dashboard is required.
- [ ] Label the saved time, measured Baseline, chosen words, and result time. Refresh offers a new Assessment; an older result remains honestly identified.
- [ ] Make reuse of an older captured Baseline visible when the source has changed; define explicit capture/refresh behavior instead of treating an existing database row as proof that the source is current.
- [ ] Test refresh-after-run, Selection edits, project switching, two runs, wrong-project IDs, mixed-invocation IDs, missing artifacts, app restart, and exporting a retained result after the source project changes.

**Exit:** A test inspects run A, makes run B/current data different, exports A, and proves every exported artifact belongs to A. No new Assessment is created by export.

### R4 — Qualify the Assessment and its interpretation

A person and ChatGPT need to distinguish no reading from incomplete search, missing evidence, and grammar-load limitations. The release must preserve those distinctions even on difficult projects.

**Files:** `src/SIL.Motif.Host/Assess/PanGlossAssessor.cs`, `src/SIL.Motif.Host/Parser/ParseMorphEvidence.cs`, `src/SIL.Motif.Host/PanGloss/BatchInvocationEvidence.cs`, `src/SIL.Motif.Commands/Assess/AssessCommand.cs`, `StatsCommand.cs`, `src/SIL.Motif.App/Views/AssessPanel.axaml`, `StatisticsPanel.axaml`, parser/command/App tests.

- [ ] Pin positive, completed-empty, capped, timed-out, skipped/invalid, ambiguous, and multiple-approved-reading cases through storage, viewing, and export.
- [ ] Retain every ordered source reference, guessed-text marker, unavailable reason, approved expectation, matched/unmatched result, warning, and declared search limit.
- [ ] Explain that Correctness means reproducing the recorded approved morphology, not proving the grammar linguistically correct; words without expectations remain distinct.
- [ ] Validate retry selection, pasted Unicode words, all wordforms, and chosen Texts against the exact recorded Selection.
- [ ] Bind retry sources to an explicit Assessment on the matching Baseline, or visibly refuse. The current newest Proposal-free ParseTime lookup does not check the Baseline token; test retry after Baseline refresh.
- [ ] Check the supported project corpus for parser constructs that silently lose source identity or analysis. Fix a demonstrated blocker for that corpus or explicitly exclude it with visible diagnostics.
- [ ] Treat process circumfixes and other known PanGloss gaps as supported-corpus qualification questions. FFI, WASM, additional engines, and exhaustive external consumer inventories do not automatically block 0.1.0.

**Exit:** The release matrix contains expected findings and failure labels, not merely successful process exit codes. Parser limitations cannot masquerade as complete, trustworthy empty evidence.

- [ ] Export AI-readable Baseline grammar and selected Text evidence from the retained source, plus the source-reference information needed to interpret parser GUIDs.
- [ ] Export per-word completion, ordered readings, approved expectations/comparisons, unavailable reasons, grammar warnings, and statistics. Keep lossless structured records beside a concise human summary.

## 5. Dependency order and parallel work

Fix the identity of the exported result before polishing its presentation. Investigate packaging and ChatGPT early because either can change the file contract or supported platform assumptions.

```text
R1 scope + decisions
  ├─ R2 retained result ── R5 complete Handoff ── R6 ChatGPT acceptance
  ├─ R3 Baseline qualification ─┐
  ├─ R4 Assessment qualification ├─ R7 desktop acceptance ─┐
  ├─ R8 recovery/storage ────────┘                        │
  └─ R9 parser release ── R10 clean-machine package ─ R11 release CI
                                                         │
                         all required exits ───────────── R12 pilot/release
```

Run the small ChatGPT-container experiment and clean-machine packaging prototype during the first wave, before committing to their final implementations. Parallel ownership can split into result/Handoff, desktop, and parser/packaging; each implementation lane uses its own clean worktree, with managed builds coordinated.

No fixed ship date is justified yet. The main uncertainties are actual ChatGPT ingestion, installed native dependencies, retained-result export, and supported-project qualification. Estimate each bounded implementation after those experiments; do not derive completion percentages from test counts or old milestone checkboxes.

## 6. Release acceptance checklist

Every item below is required for the supported 0.1.0 envelope. Where a feature is deliberately outside that envelope, the limitation must be visible and documented before release.

- [ ] No Proposal or mutation functionality is exposed by the 0.1.0 package.
- [ ] A clean supported machine installs and launches the package without developer tools.
- [ ] A supported project produces a coherent Baseline and remains byte-for-byte unchanged.
- [ ] The Assessment has explicit Baseline, Selection, scope, version, and invocation identity.
- [ ] Complete, partial, absent, and unavailable findings remain distinguishable after reopening.
- [ ] Handoff exports the selected retained result without a new Assessment or silent source refresh.
- [ ] The package contains both usable Baseline material and the full supported Assessment evidence.
- [ ] The standalone package validates, and the documented ChatGPT upload/question workflow succeeds.
- [ ] Cancellation, shutdown, failure, recovery, and storage cleanup meet their tested contracts.
- [ ] Native usability passes on the declared display/accessibility matrix.
- [ ] Required real-parser and release-artifact checks pass; remaining skips and parser limitations are adjudicated.
- [ ] Parser dependencies are publishable/retrievable, and release versions/checksums/notices match the artifact.
- [ ] The pilot, documentation, support path, and final download verification are complete.

## 7. External guidance and limits

ChatGPT's upload capabilities are a changing dependency, so the release must test its chosen route and document the account used. The published guidance supports structured/text data but does not establish that an arbitrary nested Handoff folder or archive will be ingested completely.

Checked on 2026-09-15: OpenAI's [File Uploads FAQ](https://help.openai.com/en/articles/8555545-file-uploads-faq) describes plan-dependent upload allowances and size limits. [Data analysis with ChatGPT](https://help.openai.com/en/articles/8437071-data-analysis-with-chatgpt) lists JSON/XML/YAML/text/Markdown among supported data types, notes that availability varies, and states that its Python environment cannot fetch external web resources. Therefore ship the required references inside the Handoff and prove the primary upload route; do not require fetching the latest GitHub files or hard-code one account's quota as a permanent product guarantee.

### Second wave: the released command boundary

The first release is named 0.1.0 rather than 1.0. That is a promise about maturity, not a change of
scope: the workflow it ships is still Baseline → Assessment → Handoff, and Proposal authoring is still
outside it. Naming it 0.1.0 keeps the pre-alpha permission to refuse an old stored shape instead of
migrating it, and reserves 1.0 for the release that actually carries Proposal work. Every reference in
this plan now reads 0.1.0; the one item that still names 1.0 is the no-migration boundary itself, which
belongs to the real 1.0 and not to first release.

The command boundary is a classification, not a second build. Each catalogued command declares whether
it is in the released surface or is developer-only. Released help prints only released verbs, released
dispatch refuses a developer verb before it parses that verb's arguments or registers the project, and
`MOTIF_DEVELOPER_COMMANDS=1` re-enables the whole catalog for development and for the existing suite.
Three alternatives were considered and rejected: compiling the developer verbs out through a build
configuration, which yields two binaries from one source against ADR 0040's one-artifact rule; a gate
with no opt-in at all, which would cost the suite its CLI-level Proposal coverage; and deleting the
Proposal surface outright, which discards working, tested code that the next release needs.

The released verb set is wider than the strict workflow. The corpus verbs ship although their only
current consumer — `promote-gloss` — does not, and the queue-ordering verbs `jobs requeue` and
`jobs move` ship alongside `jobs cancel`. Both are the owner's call, recorded here so that a later
reader does not mistake them for an oversight.

Statistics loses its Proposal selector in the same lane, which is the R1 item that said so, and
`Directory.Build.props` gains a declared `0.1.0` version — until now every assembly defaulted silently
to `1.0.0.0`, which the packaging lane was already stamping into artifacts.

### Second-wave handback: the boundary holds, and two things it uncovered

The released command boundary is in place and gated. Every catalogued command declares its surface, the
released executable prints only released verbs, and a developer verb is refused before it parses its own
arguments or registers the project. The partition was checked against the owner's list in both
directions: 22 released, 25 developer, 47 total, nothing in neither.

**Verification note, because it nearly produced a wrong conclusion.** The lane's own run reported 1,700
passed and 27 skipped against a recorded baseline of 1,701 and 19, which reads as a regression that
disabled eight tests. It was not one. The baseline was measured with `MOTIF_PANGLOSS_EXE` set and the
lane's run was not, and the two numbers are not comparable. Re-measuring base and branch under identical
conditions, and diffing the skip *lists* rather than the counts, gives 1,701 → 1,709 with the same 19
skips. A test count is only evidence when the parser configuration behind it is stated.

Two defects surfaced. Declaring a truthful `0.1.0` broke store opening, because the assembly version
feeds the store's minimum-worker check and that floor was a hard-coded `1.0` — a literal that had only
ever matched the version .NET supplies when none is declared. The floor is now `0.1`, and the version
itself is read from the assembly in one place rather than the nine it was spread across, two of which
still claimed `1.0` after the rename.

The second is recorded as `docs/issues.md` D17 and is older than this lane: parser discovery prefers any
executable named `pangloss` beside the application, and under test that directory held the suite's own
fake. `RealParserFact` therefore ran against a fake instead of skipping — the outcome its own
documentation warns about. Every gate so far set the parser override, which wins over discovery, so the
runs that would have caught it were exactly the ones that hid it. The fake no longer lands there.
Discovery still trusts whatever it finds, which is the check R9 already asks for.

Remaining for R1: the packaged entry-point inventory, and the decision on whether Worker ships as an
executable at all. The R2/R5 consumers are next and are blocked on the ChatGPT container experiment,
which needs the owner's account and a manual upload before the export contract can be frozen.

### The first real Handoff, and what a reader with no other context made of it

The release target changed: the Handoff must work with **whichever chat model the user has** — Claude,
ChatGPT or Gemini — rather than ChatGPT alone. That tightens the export contract rather than loosening
it, because the package can now only rely on what all three do, and it makes the reader script a
question rather than a mechanism.

So the experiment was run against a real artifact instead of a description of one. A Handoff was
generated through the production entry point with the real parser over a synthetic seeded project — 17
files, 132 KB, nested two deep — and handed to a fresh model with read-only access to that folder, no
repository, no web, and no other context. It was asked what the folder is, what ran, what the numbers
are, what produced it, and what it would still need.

**The content carried itself.** Every factual question came back right, with file-and-record citations:
both words, the `all-wordforms` provenance, both completing with zero passes and neither capped nor
timed out, the slowest word at 79,400 ns and the run at 114,500 ns, and the observation that
`statistics.md` rounds where the JSONL keeps nanoseconds. Unprompted, it separated *this run returned no
analysis* from *the corpus holds an approved analysis for that same word* — which is the
approved-reading mismatch case R6 asks for, answered correctly without being told the distinction
exists.

**It could not run the reader at all.** No Python was available to it, `read_handoff.py` never
executed, and every answer above was reached without it. That is the strongest evidence yet that the
files must be self-explaining and the reader is a convenience: on the evidence here, it already is one.
Whether to keep a Python reader, add a second one, or demote it stays open until the same package has
been put through the three products' actual upload paths.

**It did not invent provenance, and there is none to invent.** Asked which Motif version, which parser
version and which Baseline, it reported all three absent and explicitly refused the near misses —
`version: 1` is the grammar format's, `activeParser` is a project setting, `engine: "hc"` is an engine
label, and none is a software version. The refusal is the good news; the absence is R5's unbuilt
manifest, now confirmed against a real package rather than inferred from code.

Four findings are recorded in the issues log: a package that names no language (B47), a package that
says `xAmple` in one file and `hc` in another (B48), a zero-analysis result with no word-level reason
(B49), and a blank LibLCM project failing in the parser with a panic string where R3 promises an
actionable refusal (D18).

**Still not tested, and not testable from here:** whether any product's uploader ingests a nested
folder completely. A model reading files from disk never touches an upload pipeline, so nothing above
speaks to it. That half needs the folder attached in a real chat session, and the package is now
generated on demand by a skipped-by-default harness so it can be regenerated whenever that happens.
