# Proposals as pull requests: a design review

**In plain terms:** an independent read of Motif as it stood on 2026-09-24, asking how much of a pull-request style workflow (Proposals, checks, rebasing, merging) already exists, what the new per-project Overview needs from storage, and where the new direction conflicts with earlier decisions. The claims about missing Receipt rows, the absent approve verb, the 2026-08-31 lifecycle amendment and ADR 0035's reader-initiated rerun rule were checked against the code before this note was kept. The owner has since ruled on the conflicts in section E; see the app shell redesign plan of the same date.

---

Motif already has much of a PR style backend: immutable Proposal revisions, scratch Dry Runs, Trials that produce Assessments, a durable job queue, and guarded Apply. The loop is incomplete, though: Check Runs and rebase are not implemented, the Apply path does not record a durable Motif Receipt, and the App has no working Proposal review or apply surface. The existing App centers on Baseline, Selection, Assessment, results, and Handoff; the new Overview can build on its saved evidence, but needs a shared data model and new queries. (`CONTEXT.md`; `src/SIL.Motif.Worker/Jobs/TrialJobHandler.cs`; `src/SIL.Motif.Commands/ProposalCommands.cs`; `src/SIL.Motif.App/ViewModels/WorkflowStage.cs`)

## B. The PR/CI analogy, mapped concretely

| PR concept | Motif concept | What is missing or different |
|---|---|---|
| PR | **Proposal** (`CONTEXT.md` — `Proposal`) | The durable object and lifecycle exist, but human review and approval do not. `Proposal` is the binding term; the glossary explicitly avoids calling it a PR. (`docs/proposal-lifecycle.md`; `src/SIL.Motif.Commands/ProposalCommands.cs`) |
| Commits | **Proposal revisions** | Revisions are immutable and digest keyed, but the schema has no parent revision pointer or branch graph. (`src/SIL.Motif.Host/Store/MotifSchema.cs`; `CONTEXT.md` — `Draft`) |
| CI checks | **Trial**, with a Dry Run and one or more Assessments; a **Check Run** would freeze a Report as Proposal evidence | Trial and stored Reports exist. The Check Run binding, result history, and named required checks do not. (`src/SIL.Motif.Worker/Jobs/TrialJobHandler.cs`; `src/SIL.Motif.Commands/ReportCommands.cs`; `CONTEXT.md` — `Trial`, `Check Run`) |
| Base branch moving | **Baseline** changing, producing **Drift** or stale Assessment evidence | Baseline tokens and Drift checks exist. A Baseline is currently a single project row that gets replaced; rebase is not implemented. (`src/SIL.Motif.Worker/Baselines/BaselineRepository.cs`; `src/SIL.Motif.Worker/Projects/ProjectFreshnessTracker.cs`; `CONTEXT.md` — `Baseline`, `Drift`) |
| Rebase | Recompute allowed Baseline relative evidence and anchors | Design only. Rule 6 prohibits changing target, verb, value, identity, create/delete intent, or operation order. (`CONTEXT.md`; `docs/adr/0026-order-is-declared-not-positional.md`) |
| Merge | **Apply plus Receipt** | Apply exists, but its Receipt is not recorded in the Motif `Receipts` table; Apply is not queued. (`src/SIL.Motif.Commands/ProposalCommands.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`; `CONTEXT.md` — `Receipt`) |
| Merge conflicts | **Conflict** | The glossary’s `Conflict` means Motif’s store and the project’s applied history disagree. It is not a merge conflict resolver; same slot collisions are already prohibited in finalized Proposals. (`CONTEXT.md` — `Conflict`; `docs/adr/0026-order-is-declared-not-positional.md`) |
| Required checks | **Readiness** | Readiness is a computed Apply precondition, not human approval. It does not yet select or enforce a set of named Check Runs; `--force` bypasses its reasons. (`src/SIL.Motif.Host/Assess/Readiness.cs`; `src/SIL.Motif.Commands/ProposalCommands.cs`; `CONTEXT.md` — `Readiness`) |
| Code review | No current equivalent | `show`, `comment`, `reject`, and `defer` are not a threaded review or approval record. The lifecycle amendment removed `approve`; the `Decisions` table remains in the schema, but the current lifecycle does not record agreement. (`src/SIL.Motif.Commands/Catalog/CommandCatalog.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`; `docs/proposal-lifecycle.md`) |

## C. What already supports the Overview

**Stored evidence today.** The `Baselines` table stores one current Baseline’s project identity, snapshot and bundle digests, capture and publication times, and source last write time; the bundle itself is a file. `Assessments` retain Selection words and hash, Selection provenance, Assessor, Assessment kind, scope and scope digest, Baseline token, grammar source hash, per word outcomes and elapsed time, morphology and correctness evidence, and an optional timing cache path and digest. `RetainedInvocations` groups related Assessments with the Selection descriptor and expected kinds. (`src/SIL.Motif.Host/Store/MotifSchema.cs`; `src/SIL.Motif.Worker/Store/RetainedInvocationRepository.cs`; `src/SIL.Motif.Worker/Baselines/BaselineRepository.cs`; `CONTEXT.md` — `Baseline`, `Selection`, `Assessment`)

PanGloss warning lines are kept in invocation evidence; a grammar query can also return parser load warnings and grammar health findings. These are not the same record: the latter is computed by `GrammarCheckQuery`. Jobs persist their inputs, progress, results, state, and queue position. The Machine store tracks a Known project’s `LastSeenUtc`, but that is not a first import time. (`src/SIL.Motif.Host/Assess/PanGlossAssessor.cs`; `src/SIL.Motif.Commands/Queries/GrammarCheckQuery.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`; `src/SIL.Motif.Host/Store/MachineSchema.cs`; `src/SIL.Motif.Commands/Queries/KnownProjectsQuery.cs`)

The App already has a project summary with Baseline status, latest Assessment, warning summary, and history, plus Selection, Results, Difference, Statistics, and Handoff screens. It has a manual “Refresh Baseline” button. The project summary reader reports a lexicon entry count, not the requested word and rule inventory. The history query returns the current Baseline and Assessment runs; it says Baseline capture history is not stored, and it does not record Handoff writes. (`src/SIL.Motif.App/Views/ProjectPanel.axaml`; `src/SIL.Motif.App/ViewModels/WorkflowStage.cs`; `src/SIL.Motif.Projection/ProjectSummary.cs`; `src/SIL.Motif.Commands/Queries/ProjectHistoryQuery.cs`)

**Missing for “the Baseline, explained.”** `assess` stores per word elapsed time and object timing evidence, but Stats queries PanGloss on demand; the App shows a slowest word, not worst/median/95th percentile summaries. `Correctness` measures reproduction of approved analyses. The App can classify emitted readings against rejected analyses for a displayed result, but the stored correctness evidence does not measure rejected expectations as a separate result. (`src/SIL.Motif.Host/Assess/PanGlossAssessor.cs`; `src/SIL.Motif.Commands/Assess/StatsCommand.cs`; `src/SIL.Motif.App/ViewModels/StatisticsViewModel.cs`; `src/SIL.Motif.App/ViewModels/AssessWordsViewModel.cs`; `docs/adr/0038-expectations-are-fieldworks-approved-analyses.md`; `CONTEXT.md` — `Correctness`, `Approved expectation`)

There is no persisted default `Selection`: each Assessment records its own exact word list. `.motif.toml` declares Assessment scopes and a query string, but the configuration docs explicitly distinguish that query from a resolved `Selection`. There is also no combined Overview query or CLI drill-down for freshness, coverage, accuracy, or timing percentiles. `assess` reuses a stored Baseline row without checking whether the `.fwdata` changed; the Worker’s automatic Baseline refresh only unblocks a parked Dry Run. (`src/SIL.Motif.Host/Config/ProjectConfiguration.cs`; `src/SIL.Motif.Commands/Assess/AssessCommand.cs`; `src/SIL.Motif.Worker/Program.cs`; `docs/cli-api.md`; `CONTEXT.md` — `Selection`, `Assessment scope`)

**Minimal shared model.** Keep these as Motif concepts, with one typed query layer used by CLI and App under ADR 0043:

- **`SelectionPreset`**: a named, persisted default `Selection` definition for the chosen texts and added words. On a Baseline, resolve it to a full word list, provenance, and digest, then record that exact result on each Assessment. Keep it separate from `Assessment scope`.
- **`Baseline` plus a `BaselineSummary` projection**: key project counts, source fingerprint, capture time, and `BaselineFreshness` (`Current`, `KnownOld`, or `CurrentnessNotChecked`) to the Baseline token. A projection can also report that freshness could not be checked. Current freshness primitives exist, but the Overview query does not use them. (`src/SIL.Motif.Worker/Projects/ProjectFreshnessTracker.cs`)
- **`RetainedInvocation` and its member `Assessments`**: reuse the current group as the Overview’s measured evidence. Add explicit stored summaries for Selection parse completion, Correctness against `Approved expectation`, rejected reading findings, grammar warnings, and timing percentiles, each tied to the same Baseline token, Selection digest, and Assessment scope.
- **`ProjectOverview` and `OverviewDetail`**: read only projections over a selected Baseline and its retained evidence; support overview plus counts, Selection completion, Correctness, timing, and warnings drill-downs. Expose the same typed query through CLI verbs and the App, rather than implementing two metric definitions. (`docs/adr/0043-one-command-catalog-two-front-ends.md`)

Call the word metric “Selection completion” or state its exact denominator. The glossary defines `Selection` as an explicit list, while grammar coverage is parse coverage over a named `Corpus`; the default texts plus added words should not silently become a `Corpus`. (`CONTEXT.md` — `Selection`, `Assessment`, `Coverage`)

## D. The Overview as a Proposal’s view

The same `ProjectOverview` projection can accept either Baseline evidence or Proposal evidence. For a Baseline, it reads the Baseline’s own `RetainedInvocation` and Assessments. For a Proposal, it reads the Trial’s Dry Run and Assessments attached to the exact Proposal revision, then adds its semantic operations and Dry Run effects. The store already supports `ProposalId` and `ProposalIntentDigest` on an Assessment, which gives a starting link. (`src/SIL.Motif.Host/Store/MotifSchema.cs`; `src/SIL.Motif.Worker/Jobs/TrialJobHandler.cs`; `CONTEXT.md` — `Proposal`, `Trial`)

For that shared view to be trustworthy, each Trial needs a complete evidence identity: Proposal intent digest, Baseline token and semantic snapshot digest, resolved Selection digest, Assessment scope digest, Assessor and version, grammar source fingerprint, and any parser or statistics artifact digest. The Assessment schema has many of these fields, but some are optional; `PanGlossAssessor` constructs results with several fingerprint slots null. The actual Trial must be rejected as stale for a displayed Proposal revision if its intent digest no longer matches. (`src/SIL.Motif.Host/Store/MotifSchema.cs`; `src/SIL.Motif.Host/Assess/PanGlossAssessor.cs`; `src/SIL.Motif.Worker/Jobs/TrialJobHandler.cs`; `docs/adr/0042-a-job-produces-assessments-an-assessor-makes-them.md`)

`Difference` is already an Assessment kind and `compare` stores it, so it can supply the shared word by word comparison. It does not make the comparison a verdict: keep Assessor and kind aligned, identify the exact Selection and scope, and show missing or incomplete evidence. (`src/SIL.Motif.Commands/CompareCommands.cs`; `src/SIL.Motif.Host/Assess/AssessmentComparison.cs`; `docs/adr/0042-a-job-produces-assessments-an-assessor-makes-them.md`; `CONTEXT.md` — `Difference`, `Assessment`)

A Proposal’s **Check Run** should freeze the revision digest, Baseline token, Selection digest, scope, Assessment and Report ids, and tool versions it evaluated. It should retain the outcome when later work changes those inputs. Current Reports store Assessment and Selection evidence, but there is no Check Run record binding that evidence to a required check policy or Readiness result. (`src/SIL.Motif.Commands/ReportCommands.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`; `CONTEXT.md` — `Check Run`, `Readiness`)

## E. Risks and contradictions

- **Human review vs. current lifecycle:** the owner’s 1.0 direction calls for a person to review AI Proposals before pushing them. The current Proposal amendment removed approval and says nothing records who agreed. Resolve this as a distinct human Review or Decision that precedes Apply, separate from mechanical `Readiness`; otherwise the roadmap describes a gate the product explicitly removed. (`docs/proposal-lifecycle.md`; `src/SIL.Motif.Commands/ProposalCommands.cs`; `CONTEXT.md` — `Readiness`, `Apply Authorization`)
- **Report and regression policy:** `CONTEXT.md` says a `Report` is “Advisory always,” but ADR 0035 was amended by ADR 0042 to allow configured regressions to block Apply; the code implements that gate through Readiness and Correctness evidence. Clarify that a Report remains advisory while a separately named Readiness policy may block, or revise the glossary and ADRs if Reports themselves become required checks. Also, ADR 0042 says an override is recorded as a `Decision`, while current `--force` does not write one and the lifecycle amendment removed the override comment. (`docs/adr/0035-reports-are-advisory-queries-over-stored-assessments.md`; `docs/adr/0042-a-job-produces-assessments-an-assessor-makes-them.md`; `src/SIL.Motif.Commands/ProposalCommands.cs`; `docs/proposal-lifecycle.md`)
- **Automatic reruns:** the request to run when stale conflicts with ADR 0035’s rule that rerunning is the reader’s decision, and needs an explicit decision about whether the stale action queues a Baseline refresh, a new Assessment, or both. ADR 0042 already permits lazy Baseline refresh when something next needs it; that does not define unattended Assessment reruns. (`docs/adr/0035-reports-are-advisory-queries-over-stored-assessments.md`; `docs/adr/0042-a-job-produces-assessments-an-assessor-makes-them.md`; `src/SIL.Motif.Worker/Program.cs`)
- **What “everything in SQLite” means:** the `Motif store` glossary says nothing about a project lives elsewhere, but ADR 0041 explicitly keeps Baseline bundles, Dry Run scratches, PanGloss workspaces, and `.fwdata` as files. Project configuration is also read from `.motif.toml`. Define SQLite as the home for Motif records and queryable summaries, while other programs’ required artifacts remain files, or supersede ADR 0041 and the configuration contract. (`CONTEXT.md` — `Motif store`; `docs/adr/0041-the-database-is-the-only-store.md`; `src/SIL.Motif.Host/Config/ProjectConfiguration.cs`)
- **FieldWorks integration is not built:** the current `apply` command takes one Proposal id; the planned `apply --all-pending` save boundary integration is absent from the CLI catalog. That leaves the 0.2 push back to FieldWorks and later apply workflow as separate work. (`src/SIL.Motif.Commands/Catalog/CommandCatalog.cs`; `docs/adr/0043-one-command-catalog-two-front-ends.md`; `AGENTS.md` — Compatibility targets)
- **Keep AI authoring at Layer 1:** the 1.0 direction can expand the semantic Proposal vocabulary across FieldWorks data, but a generic field setter would reverse ADR 0029. Each new capability needs a named Intent/composer and the corresponding operation family. (`docs/adr/0009-layered-api-primitives-and-composers.md`; `docs/adr/0029-agents-address-layer-1-only.md`; `CONTEXT.md` — `Intent`, `Motif operation`)
- **The written status is inconsistent:** `docs/plan-motif.md` still describes a CLI and future FieldWorks integration as delivery, while `docs/adr/0043-one-command-catalog-two-front-ends.md` and the current App implement a Motif owned front end. `README.md` says the paired database and durable job system are not built, while current source contains both. Use the code and ADR 0043 for the current status, then align the roadmap and README. (`docs/plan-motif.md`; `README.md`; `src/SIL.Motif.Worker/Program.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`)

## F. Recommended build order

1. **Settle the contracts in writing.** Define Selection completion versus Corpus coverage, which parts of stale work run automatically, what a human Review means, and what “in SQLite” covers. Update `CONTEXT.md` and supersede affected decisions in ADR 0035, 0041, and 0042. This is independently shippable documentation and prevents Overview metrics from taking conflicting meanings.
2. **Add the import wizard and saved Selection.** Let first open choose default texts and added words, persist a named `SelectionPreset`, and show the resolved Selection digest. Retain per Assessment the exact resolved words and provenance, as the existing `Selection` contract requires. (`src/SIL.Motif.App/ViewModels/ProjectViewModel.cs`; `src/SIL.Motif.Commands/Assess/SelectionComposer.cs`; `CONTEXT.md` — `Selection`)
3. **Publish Baseline facts.** Record word, rule, and project counts against the Baseline token and expose current, old, or unchecked freshness. Preserve the existing file backed Baseline artifacts; decide separately whether replaced Baselines need retained history. (`src/SIL.Motif.Host/Store/MotifSchema.cs`; `src/SIL.Motif.Worker/Projects/ProjectFreshnessTracker.cs`; `docs/adr/0041-the-database-is-the-only-store.md`)
4. **Schedule stale Baseline Assessments.** Add a durable assessment Job that uses the saved Selection and declared scope, retains its `RetainedInvocation`, warnings, correctness, and timing evidence, and can be observed, cancelled, or retried. Keep `apply` out of this automatic loop. This deliberately supersedes ADR 0035’s reader initiated rerun rule if unattended runs are the chosen behavior. (`src/SIL.Motif.Worker/Jobs/JobStateMachine.cs`; `src/SIL.Motif.Worker/Store/RetainedInvocationRepository.cs`; `docs/adr/0035-reports-are-advisory-queries-over-stored-assessments.md`)
5. **Ship the shared Overview and drill-downs.** Add a typed `ProjectOverview` query to the command catalog, with CLI verbs for overview and its metric details; render the same projection in the App. Define accuracy against approved and rejected analyses and compute worst, median, and 95th percentile from retained timing data. (`src/SIL.Motif.Commands/Catalog/CommandCatalog.cs`; `src/SIL.Motif.App/Services/ICommandClient.cs`; `docs/adr/0043-one-command-catalog-two-front-ends.md`)
6. **Give Proposals the same Overview and real CI evidence.** Display Trial evidence through the same projection, add Check Runs bound to exact Proposal revision and Baseline evidence, then implement only the permitted rebase refreshes. Keep `Difference` as an Assessment, and derive Readiness from its declared evidence. (`src/SIL.Motif.Worker/Jobs/TrialJobHandler.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`; `CONTEXT.md` — `Difference`, `Check Run`; `AGENTS.md` — design rule 6)
7. **Build the to do list and review path.** Connect existing Handoff, Baseline refresh, and Job status to Overview findings; turn the App’s transient analysis changes into supported Proposal operations and human review, then Apply and a durable Receipt. Add FieldWorks integration at its planned save boundary separately. (`src/SIL.Motif.App/ViewModels/ChangesViewModel.cs`; `src/SIL.Motif.Commands/ProposalCommands.cs`; `src/SIL.Motif.Host/Store/MotifSchema.cs`; `docs/adr/0043-one-command-catalog-two-front-ends.md`)
