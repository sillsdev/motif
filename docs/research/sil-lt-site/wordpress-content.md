SIL’s product sites organize product information into pages for features, downloads, help, and news. Motif can keep its current help content portable while giving site-owned pages enough structure to move into WordPress later.

Retrieved 2026-09-28.

# Scope and method

I reviewed the public SIL Language Technology home and software catalog, product pages for FieldWorks, Phonology Assistant, WeSay, SayMore, Lexique Pro, Cog, FLExTrans, and PAWS, and WordPress documentation. Bloom’s product page could not be retrieved; I used only its catalog entry and SIL’s site-level Bloom news, and did not substitute Bloom Library. The product catalog identifies these products and links to their product pages under “Software Products Catalog” and “Search & Filter” ([Software Products Catalog](https://software.sil.org/software-products/)).

The lead supplied root-site and FieldWorks-subsite REST and HTML snapshots in `.tmp/sil-raw/`; I reviewed those on 2026-09-28. Each supplied page response contains 100 records, so hierarchy and template counts below describe the snapshots rather than a complete site export ([root REST index](../../../.tmp/sil-raw/json/root_index.json), [FieldWorks REST index](../../../.tmp/sil-raw/json/fieldworks_index.json), [raw files](../../../.tmp/sil-raw/)).

# WordPress structure and migration evidence

## REST API structure

The supplied snapshots confirm separate root and `/fieldworks/` REST indexes for the WordPress multisite. Both indexes expose `/wp/v2/pages`, `/posts`, `/types`, `/taxonomies`, `/categories`, and `/menus`; the FieldWorks index is a separate site endpoint, not merely a root-site page path ([root REST index](../../../.tmp/sil-raw/json/root_index.json), `routes`; [FieldWorks REST index](../../../.tmp/sil-raw/json/fieldworks_index.json), `routes`).

The public types endpoint describes which resources each site exposes. Editorial types and notable differences in the snapshots are:

| Site | Type | Hierarchy and taxonomies in REST type record |
|---|---|---|
| Root | `page` | Hierarchical; supports `category` and `post_tag` |
| Root | `post` | Not hierarchical; supports `category` and `post_tag` |
| Root | `software` | Custom, not hierarchical; uses `software_category`, `operating_system`, and `supported_status` |
| Root | `awsm_job_openings` | Custom, not hierarchical; uses `job-skills` |
| FieldWorks | `page` | Hierarchical; no taxonomies listed |
| FieldWorks | `post` | Not hierarchical; supports `category` and `post_tag` |

Both sites also expose media attachments and WordPress system types for menus, reusable blocks, templates, navigation, global styles, and fonts. The root has two custom editorial types (`software` and `awsm_job_openings`); the FieldWorks type snapshot has no `software` type or custom editorial type. These values come from each site’s type and taxonomy responses ([root types](../../../.tmp/sil-raw/json/root_wp_v2_types.json), `rest_base`, `hierarchical`, `taxonomies`; [root taxonomies](../../../.tmp/sil-raw/json/root_wp_v2_taxonomies.json), `types`; [FieldWorks types](../../../.tmp/sil-raw/json/fieldworks_wp_v2_types.json), same fields; [FieldWorks taxonomies](../../../.tmp/sil-raw/json/fieldworks_wp_v2_taxonomies.json), `types`).

The root’s `software` facets are explicit taxonomies: product category, operating system, and support status. The root category response contains Home, Learn, News, and Uncategorized; the FieldWorks category response contains only Uncategorized (73 associated posts in this snapshot). FieldWorks posts are categorized separately from its Pages; the root API also permits categories and tags on Pages ([root categories](../../../.tmp/sil-raw/json/root_wp_v2_categories.json), `name`, `slug`, `count`; [FieldWorks categories](../../../.tmp/sil-raw/json/fieldworks_wp_v2_categories.json), same fields; type and taxonomy snapshots linked above).

## Page hierarchy and templates

The FieldWorks pages form a real parent tree matching the visible URL nesting: `Downloads` (`id 18`, parent `0`, menu order `6`) → `Version 9.3` (`id 4980`, parent `18`, menu order `1`) → `FieldWorks 9.3.10/11` (`id 5337`, parent `4980`, menu order `4`). Other top-level pages in the snapshot include Features, News, and Get Help and Training. The sampled pages’ `template` values are empty; the captured Download HTML body uses `page-template-default` with the `wp-theme-web-productsites` and `fieldworks` classes ([FieldWorks pages](../../../.tmp/sil-raw/json/fieldworks_wp_v2_pages.json), `id`, `slug`, `parent`, `template`, `menu_order`; [download page rendered content](../../../.tmp/sil-raw/json/fieldworks_download_content.json), `id 18`; [download HTML](../../../.tmp/sil-raw/html/fieldworks_download.html), `body` class).

The root page snapshot also contains hierarchical Pages. Its `Software Products Catalog` page (`id 11814`) is top-level, has menu order `1`, and uses `page-software-catalog.php`; `Learn` (`id 15641`) uses `page-blog.php`; most of the 100 root records have an empty `template` value. The snapshot also includes `page-fonts-catalog.php`. The captured product pages use the same `wp-theme-web-productsites` theme and a product-specific body class; Cog, for example, uses the default page template ([root pages](../../../.tmp/sil-raw/json/root_wp_v2_pages.json), `id`, `slug`, `parent`, `template`, `menu_order`; [software catalog HTML](../../../.tmp/sil-raw/html/software-products.html), `body` class; [Cog HTML](../../../.tmp/sil-raw/html/cog.html), `body` class).

The API index exposes GET and write routes for `/wp/v2/menus` and `/wp/v2/menus/{id}` on both sites, and each type index lists `nav_menu_item`. The menu route schema includes `locations` and `auto_add`, but the supplied files do not include menu-record responses, so actual menu IDs, locations, and item-to-page relationships are not available here. The FieldWorks HTML does show rendered navigation labels and destinations; `menu_order` on a Page is useful ordering metadata, but by itself is not a complete menu export ([root REST index](../../../.tmp/sil-raw/json/root_index.json), `/wp/v2/menus` route schema; [FieldWorks REST index](../../../.tmp/sil-raw/json/fieldworks_index.json), same schema; [FieldWorks download HTML](../../../.tmp/sil-raw/html/fieldworks_download.html), navigation links).

## Product navigation and site boundaries

The rendered FieldWorks navigation has product-specific groups and links, while the REST page records confirm the parent tree behind the Download → Version 9.3 → 9.3.10/11 path ([FieldWorks download HTML](../../../.tmp/sil-raw/html/fieldworks_download.html), navigation links; [FieldWorks pages](../../../.tmp/sil-raw/json/fieldworks_wp_v2_pages.json), `parent`, `menu_order`). WordPress keeps menu records distinct from hierarchical page parentage, so Motif should retain both structures ([Create Pages](https://wordpress.org/documentation/article/create-pages/), “Create a Page”; [Navigation Menus REST API](https://developer.wordpress.org/rest-api/reference/nav_menus/), “Schema”).

The SIL home and catalog link Keyman and Paratext to `keyman.com` and `paratext.org`, respectively; treat those as linked products outside this WordPress page tree rather than assuming they migrate with SIL’s content ([SIL home](https://software.sil.org/), “Write & Communicate”; [catalog](https://software.sil.org/software-products/), “Software Products Catalog”).

## Menus, content rendering, and downloads

The FieldWorks `/download` Page’s rendered body is a conventional sequence of headings, paragraphs, and links. It points readers to child Pages for the current version, sample projects, localization packages, readme documents, spelling dictionaries, and previous releases; the Linux section links to external installation instructions. The release Page then links to installer packages and release metadata, rather than the parent download Page containing a flat list of installer binaries ([FieldWorks rendered download content](../../../.tmp/sil-raw/json/fieldworks_download_content.json), `content.rendered`; [download HTML](../../../.tmp/sil-raw/html/fieldworks_download.html), content links; [FieldWorks 9.3.10/11 release](https://software.sil.org/fieldworks/download/fw-93/fw-9310/), “Packages For Windows,” “Verifying Downloads”).

The REST file contains `content.rendered`, but not a raw editor body. That rendered content has ordinary `<h2>`, `<p>`, `<a>`, `<br>`, `<code>`, and `<hr>` markup; no shortcode token or page-builder markup was observed in it. The captured HTML body has `page-template-default`, `wp-theme-web-productsites`, and `fieldworks` classes, with no Elementor, Visual Composer, Divi, or similar builder class. **Inferred:** the page is rendered by the product-site theme’s default template and does not depend on a recognizable builder in its visible output. This evidence cannot distinguish Classic Editor from Gutenberg, because the REST snapshot omits `content.raw` and block delimiters are not present in rendered output. The global `wp-block-library` stylesheet alone does not prove Gutenberg authored this page ([download content JSON](../../../.tmp/sil-raw/json/fieldworks_download_content.json), fields and `content.rendered`; [download HTML](../../../.tmp/sil-raw/html/fieldworks_download.html), `body` class and page body; [WordPress block serialization](https://developer.wordpress.org/block-editor/explanations/architecture/data-flow/), “Serialization and parsing”).

The root REST type index exposes `attachment` at `media` on both sites, and WordPress media records can carry alt text and captions ([root types](../../../.tmp/sil-raw/json/root_wp_v2_types.json), `attachment`; [FieldWorks types](../../../.tmp/sil-raw/json/fieldworks_wp_v2_types.json), `attachment`; [Media REST API](https://developer.wordpress.org/rest-api/reference/media/), “Schema”). The supplied snapshots do not include attachment records. FieldWorks’ version page links downloadable package files directly, but this evidence does not establish whether each file is a WordPress attachment or externally hosted ([FieldWorks 9.3.10/11 release](https://software.sil.org/fieldworks/download/fw-93/fw-9310/), “Packages For Windows”).

## What Motif content will not migrate unchanged

- The site homepage and developer landing page are Astro/Starlight MDX with imported components; those component imports and component props have no direct WordPress Markdown equivalent ([site home](../../../site/src/content/docs/index.mdx), page source; [developer landing page](../../../site/src/content/docs/developers.mdx), page source; [site configuration](../../../site/astro.config.mjs), “Starlight configuration”).
- Help source uses custom `cmd:`, `term:`, `ui:`, and `shot:` links that the site sync script rewrites into site routes or assets. A WordPress importer would need equivalent resolution or rewritten ordinary links ([help example](../../../help/en/guide/what-is-motif.md), “What is Motif?”; [sync script](../../../site/scripts/sync-core.mjs), `rewriteLinks` and help output generation).
- Commands, terms, controls, API references, and walkthrough pages are generated from structured help sources or XML documentation; generated routes and components are outputs, not standalone authoring files ([sync script](../../../site/scripts/sync-core.mjs), command, term, control, API, and walkthrough generation; [content configuration](../../../site/src/content.config.ts), collections).
- The samples page is generated from sample JSON and binaries, with download links emitted by the sync script. Its source data and binary packaging need an importer or explicit asset migration ([sync script](../../../site/scripts/sync-core.mjs), sample generation; [sample specifications](../../../samples/), `sample.json` files).

The current source contract favors plain CommonMark for help and Guide pages, with custom cross-link codes resolved by the readers; homepage copy belongs to the site. Preserve that distinction when planning migration ([site content plan](../../../docs/superpowers/plans/2026-09-26-docs-content-plan.md), “Source of truth”; [site home and learn plan](../../../docs/superpowers/plans/2026-09-26-site-home-learn-samples-plan.md), “Home”; [help guide](../../../help/en/guide/what-is-motif.md), “What is Motif?”).

# What Motif's site should do

1. **Keep canonical help in the existing plain-Markdown source.** Continue authoring command, term, and Guide prose in `help/en/` using the current cross-link vocabulary; let a WordPress export adapter resolve those links to stable destination URLs. The product requires CommonMark and the current sync transforms the special links ([site content plan](../../../docs/superpowers/plans/2026-09-26-docs-content-plan.md), “Source of truth”; [sync script](../../../site/scripts/sync-core.mjs), `rewriteLinks`).
2. **Model the page tree explicitly.** Store stable slugs, a parent slug, page `menu_order`, and a semantic layout for every site-owned page. Resolve parent slugs to destination IDs at import and build menus separately; FieldWorks’ Downloads → Version 9.3 → 9.3.10/11 tree shows the parent structure, while the REST index exposes menus as a separate resource ([FieldWorks pages](../../../.tmp/sil-raw/json/fieldworks_wp_v2_pages.json), `parent`, `menu_order`, `template`; [FieldWorks REST index](../../../.tmp/sil-raw/json/fieldworks_index.json), `/wp/v2/menus`).
3. **Keep source links stable and presentation neutral.** Use relative Markdown links between source pages and explicit URLs for external resources. Resolve internal links to final WordPress slugs during export. Do not make an Astro route or a Starlight component name the only reference to a page; the current help sources use special link codes and the homepage uses imported components ([help guide](../../../help/en/guide/what-is-motif.md), “What is Motif?”; [site homepage](../../../site/src/content/docs/index.mdx), page source).
4. **Use Pages and Posts for the content Motif actually has.** Put durable Help, Guide, and feature material in hierarchical Pages; use Posts for dated release announcements. Keep release notes/download detail in a version page or structured release record under the product’s Downloads page. The SIL root’s `software` custom type and OS/support taxonomies serve its multi-product catalog; Motif should not copy that catalog schema for a single product ([root types](../../../.tmp/sil-raw/json/root_wp_v2_types.json), `software`; [root taxonomies](../../../.tmp/sil-raw/json/root_wp_v2_taxonomies.json), product taxonomies; [FieldWorks types](../../../.tmp/sil-raw/json/fieldworks_wp_v2_types.json), `page` and `post`).
5. **Treat downloadable files as linked artifacts.** Keep label, version, platform, package format, URL, size, date, release notes, and checksum together; model the version page separately from the binary file and preserve the original download URL. FieldWorks’ parent Download page links to version and resource Pages, while the version page links to installer packages ([FieldWorks rendered Download page](../../../.tmp/sil-raw/json/fieldworks_download_content.json), `content.rendered`; [FieldWorks release](https://software.sil.org/fieldworks/download/fw-93/fw-9310/), “Packages For Windows,” “Verifying Downloads”).
6. **Keep portable Markdown as source and render ordinary content.** The captured download Page renders as semantic headings, paragraphs, links, and code with no observed shortcode or builder markup. Keep presentation in a small set of semantic layouts; let the importer emit ordinary HTML or standard editor blocks, and do not make builder syntax or editor-specific serialized markup canonical ([rendered content](../../../.tmp/sil-raw/json/fieldworks_download_content.json), `content.rendered`; [download HTML](../../../.tmp/sil-raw/html/fieldworks_download.html), `body` class; [site homepage](../../../site/src/content/docs/index.mdx), page source).
7. **Separate page order from actual navigation.** Store menu name, item label, parent item, and order independently from a page’s parent slug and `menu_order`; export menu records after reading each subsite’s menu endpoint. The WordPress index exposes `/wp/v2/menus`, but no menu record snapshot was supplied ([FieldWorks REST index](../../../.tmp/sil-raw/json/fieldworks_index.json), `/wp/v2/menus`; [Navigation Menus REST API](https://developer.wordpress.org/rest-api/reference/nav_menus/), “Schema”).
8. **Make export schema-aware and repeatable.** Query each destination subsite’s types, taxonomies, page templates, menus, and media before import. Record source paths and destination IDs in an export manifest so repeated imports update the same WordPress records. The root and FieldWorks snapshots already show why assumptions must be per site: the root has custom product types and taxonomies, while FieldWorks does not ([root type snapshot](../../../.tmp/sil-raw/json/root_wp_v2_types.json); [FieldWorks type snapshot](../../../.tmp/sil-raw/json/fieldworks_wp_v2_types.json); [Pages REST API](https://developer.wordpress.org/rest-api/reference/pages/), “Retrieve a Page,” “Update a Page”).
