# FieldWorks installer research for Motif

FieldWorks is installed for the whole Windows computer, and its installer also manages shared system settings and runtimes. Motif can work alongside it safely if its own files and ICU stay isolated and FieldWorks has a stable way to locate the Motif command.

## Scope and evidence

This note compares the installer and release paths visible in the FieldWorks and FwLite source trees with Velopack’s current packaging model. The local FieldWorks checkout was at 089eb9027b6d81be7883c40960f0de3ffa04b699 (branch lt-22801-patch-component-ledger); the genericinstaller checkout was at 3e19f9be90bec04c63c35b39bb8e538fb7114a7c. These are source snapshots, not proof that every external release job or secret store is represented. Local file citations below are repository-relative paths with line numbers in those checkouts. ## Current Windows installer

### Toolset, bundle, and scope

The default FieldWorks installer remains a WiX 3 Burn bundle around a machine-wide MSI. The build project selects WiX 3 unless InstallerToolset opts into the parallel WiX 6 path; the WiX 3 targets build both the base installer and MSP patch (FieldWorks/Build/InstallerBuild.proj:19,29-30; FieldWorks/Build/Installer.Wix3.targets:30-31). The build guide identifies WiX 3.14 as the default and documents WiX 6 as opt-in (FieldWorks/Docs/installer-build-guide.md:23-27,66-69).

The online Burn chain checks or installs .NET Framework 4.8 and Visual C++ redistributables before the MSI; the MSI has ForcePerMachine=yes (FieldWorks/PatchableInstaller/BaseInstallerBuild/Bundle.wxs:24-43). The offline bundle embeds the .NET Framework installer and VC redistributables (FieldWorks/PatchableInstaller/BaseInstallerBuild/OfflineBundle.wxs:24-30,44-70,91-162,180-279). Its MSI is elevated, removes older related products, and retains a shared UpgradeCode (FieldWorks/PatchableInstaller/BaseInstallerBuild/Framework.wxs:21-42).

The source documents a .NET Framework 4.8.1 targeting pack for building, while the bootstrapper ensures .NET Framework 4.8. The exact framework target and runtime expectation of every shipped FieldWorks component are UNVERIFIED from these installer sources (FieldWorks/Docs/installer-build-guide.md:96-111; FieldWorks/PatchableInstaller/BaseInstallerBuild/Bundle.wxs:24-43).

### Files, shared state, COM, and data

The install defaults to Program Files\SIL\FieldWorks 9; harvested application data and user projects live below ProgramData\SIL, including ProgramData\SIL\FieldWorks\Projects. Installer overrides preserve an existing project/data location by reading prior 32-bit FieldWorks 8 and current-version HKLM registry values (FieldWorks/FLExInstaller/Overrides.wxi:3-15).

Custom actions and registry entries modify machine-level state: PATH, FIELDWORKSDIR, ICU_DATA, and WEBONARY_API (FieldWorks/FLExInstaller/CustomComponents.wxi:30-50). The installer also adds .fwbackup and .fwdata open verbs and the silfw: protocol (CustomComponents.wxi:127-147). On 64-bit Windows it writes FieldWorks app/data paths under WOW6432Node for 32-bit Paratext consumers (CustomComponents.wxi:182-195).

FieldWorks includes ICU 70 data and points ICU_DATA at ProgramData\SIL\Icu70 (CustomComponents.wxi:37-40; FieldWorks/Build/SetupInclude.targets:16-21; FieldWorks/Build/Installer.legacy.targets:209-213). Another registry value named ICU54DataDir points to Icu54 (CustomComponents.wxi:182-195). Whether this is stale compatibility state or an intentional second ICU data contract is UNVERIFIED; do not reuse either path for Motif until an owner resolves the mismatch.

FieldWorks installs Andika, Charis SIL, Doulos SIL, Gentium Plus, and Quivira into the Windows Fonts directory when the corresponding fonts are not already registered (FieldWorks/FLExInstaller/Fonts.wxi:3-16,82-120). It also installs TECkit components into Common Files and bundles encoding-converter components with the application (FieldWorks/FLExInstaller/CustomComponents.wxi:17-28,114-125; FieldWorks/FLExInstaller/CustomFeatures.wxi:5-12). The Encoding Converters package describes its role in FieldWorks text conversion: [Encoding-Converters-Core](https://www.nuget.org/packages/Encoding-Converters-Core/0.8.2).

FieldWorks does use COM, but the main application avoids global COM registration: build-generated registration-free manifests are shipped beside the executable to allow versions to coexist (FieldWorks/Build/RegFree.targets:38-43,48-76; CustomComponents.wxi:127-133). MSI harvesting explicitly excludes COM and registry harvesting (FieldWorks/PatchableInstaller/BaseInstallerBuild/buildMsi.bat:14-15). Whether any included third-party merge module registers COM globally is UNVERIFIED.

### Base installer and patch release model

FieldWorks distributes full online and offline Burn bundles as base releases and small MSP updates as patches. The patch build compares base and update MSI component sets and creates an MSP with WiX tools (FieldWorks/PatchableInstaller/CreateUpdatePatch/buildPatch.bat:61-90). The patch release workflow downloads the matching base build assets and runs a component-ledger check before signing and publishing (FieldWorks/.github/workflows/patch-installer-cd.yml:179-203,266-288).

The base workflow accepts an installer_ref (default master) and checks out sillsdev/genericinstaller into the FieldWorks PatchableInstaller directory (FieldWorks/.github/workflows/base-installer-cd.yml:25,85-91). Local MSBuild targets also expect that directory (FieldWorks/Build/Installer.legacy.targets:66-69,74-87). The genericinstaller README describes its reusable WiX template and submodule setup (genericinstaller/README.md:173-198), but the FieldWorks workflow’s explicit checkout is the relevant release wiring here. Since the workflow pins a ref input rather than a recorded commit in this source, the exact genericinstaller revision used by a given published build is UNVERIFIED.

## Build, CI, artifacts, and signing

FieldWorks’ build.ps1 defaults to WiX 3, can select WiX 6, and exposes -BuildInstaller, -BuildPatch, and local -SignInstaller switches (FieldWorks/build.ps1:91-106,197-200). The installer guide describes the Windows release build steps and outputs (FieldWorks/Docs/installer-build-guide.md:96-111,118-137,203-207).

The visible GitHub Actions base release runs on Windows Server 2022, is manually triggerable or weekly, builds with a number derived from the GitHub run number, and publishes online/offline bundles to SIL’s S3 update location and GitHub Release build-N (FieldWorks/.github/workflows/base-installer-cd.yml:12-16,20-68,208-239,259-296). It adds 1000 to the GitHub run number because base builds historically used Jenkins numbering (base-installer-cd.yml:9-10). Patch numbers must exceed the corresponding base build number (FieldWorks/.github/workflows/patch-installer-cd.yml:6-7,74-78), and patch outputs plus the component ledger go to the corresponding S3 patch location (patch-installer-cd.yml:266-288). Jenkins’ current role and any other out-of-repository release jobs are UNVERIFIED; the checked source establishes the historical numbering convention, not current Jenkins execution.

The base and patch workflows call sillsdev/codesign/trusted-signing-action@v3 with the secret name TRUSTED_SIGNING_CREDENTIALS; the base job signs the bundle engines and reattached bundles, while the patch job signs MSPs (FieldWorks/.github/workflows/base-installer-cd.yml:208-228; patch-installer-cd.yml:278-288). The public action is maintained at [sillsdev/codesign](https://github.com/sillsdev/codesign). Workflows also name AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY for publishing. Secret values are not part of this research. FwLite’s Windows workflow uses the same signing action and credential name (languageforge-lexbox/.github/workflows/fw-lite.yaml:490-497), which does not prove the credential scope, signing profile, certificate identity, or that another tool can use it. Those are UNVERIFIED.

No Apple Developer ID or notarization configuration was found in the checked FieldWorks installer sources. FwLite’s macOS workflow explicitly has a todo sign the app note (languageforge-lexbox/.github/workflows/fw-lite.yaml:288-320). Apple team membership, certificates, notarization credentials, and private signing jobs are UNVERIFIED; absence from these files does not establish that SIL has no Apple signing identity.

## Linux, macOS, FwLite, and ICU

FieldWorks desktop’s supported release story is currently Windows. SIL’s downloads page offers Windows releases and identifies Linux as unsupported for current releases; its FAQ says the same and directs Mac users to a Windows virtual machine ([FieldWorks downloads](https://software.sil.org/fieldworks/download/), [FAQ](https://software.sil.org/fieldworks/faq/)). The Linux installation page documents older Ubuntu packages and the FieldWorks 9.0 Flatpak route, rather than a current desktop release ([Linux installation](https://packages.sil.org/fieldworks.html)). The Flathub source labels its FieldWorks package end-of-life and was archived in May 2026 ([Flathub package source](https://github.com/flathub/org.sil.FieldWorks)). The precise relationship between the still-linked SIL installation instructions and that archived Flathub package is UNVERIFIED.

FwLite is a separate companion application, not the FieldWorks desktop installer. Its current workflow builds macOS web-app bundles for x64 and ARM64, Linux single-file binaries for x64 and ARM64, and Windows portable/MSIX packages; Windows signing uses the SIL Trusted Signing action. The workflow notes that macOS signing remains TODO. Android signing uses a separate keystore and credentials (languageforge-lexbox/.github/workflows/fw-lite.yaml:288-364,366-416,418-514; backend/FwLite/README.md:21-27). These details show build capability, not a shared FieldWorks desktop installer or a Motif packaging commitment.

ICU is a native runtime dependency for the LibLCM path. Motif’s README directs Ubuntu users to SIL’s icu-fw package and macOS users to Homebrew icu4c (README.md:330-343). LibLCM CI installs icu-fw from SIL’s experimental Ubuntu package feed (liblcm/.github/workflows/ci-cd.yml:41-48), and its agent instructions describe that dependency (liblcm/AGENTS.md:16-19,46-49). The exact supported way to redistribute ICU on Windows and the current ICU contract for old FieldWorks Flatpak builds are UNVERIFIED.

## What Velopack provides

The following separates Velopack’s built-in package behavior from work that requires application code, hooks, or a separate installer/integration. Sources: [Windows packaging](https://docs.velopack.io/packaging/operating-systems/windows), [installer options](https://docs.velopack.io/packaging/installer), [hooks](https://docs.velopack.io/integrating/hooks), [framework bootstrapping](https://docs.velopack.io/packaging/bootstrapping), [macOS packaging](https://docs.velopack.io/packaging/operating-systems/macos), [Linux packaging](https://docs.velopack.io/packaging/operating-systems/linux), and [migration guides](https://docs.velopack.io/category/migrating).

| FieldWorks concern | Velopack fit | What it means for Motif |
|---|---|---|
| Per-user app folder, stable launcher, update delivery, shortcuts, and app replacement | **Velopack does it** | Windows defaults to a per-user folder under Local AppData; the Setup creates shortcuts and launches the app. Keep Motif’s executable and private runtime files together. |
| Optional Windows per-machine install and conventional MSI shell | **Velopack does it**, with its optional WiX 5 MSI | This can address a requirement for Program Files, Add/Remove Programs, or group policy deployment. It does not recreate FieldWorks’ full custom MSI behavior by itself. |
| Supported Windows .NET and VC++ framework bootstrap | **Velopack does it** for supported frameworks | Its framework bootstrap option may cover Motif’s own prerequisites. It does not prove compatibility with FieldWorks’ full .NET Framework 4.8 bootstrap chain. |
| Short, noninteractive per-user state adjustment | **a hook can do it** | Hooks can run lifecycle scripts, but cannot display UI or cancel the install. Install/uninstall hooks have a 30-second limit; obsolete/update hooks have a 15-second limit. Use only for small, idempotent work. |
| Long migration, user choice, elevation, machine PATH or environment variables, global fonts, shared Encoding Converters, or HKLM state | **needs something else** | Velopack hooks do not provide an elevated interactive installer experience. Keep machine-wide dependencies in a separate installer or change FieldWorks to consume Motif through a user-scoped contract. |
| Registration-free COM manifests shipped beside an executable | **Velopack does it** for file delivery | Package the executable and its manifests together. Do not translate manifest-based activation into global COM registration. Any external COM registration would need separate handling. |
| Existing base MSI plus MSP patch/component-ledger model | **needs something else** | Velopack’s app-folder update model is not WiX MSP servicing. Plan to replace the FieldWorks patch integration, not wrap it in Velopack. |
| Adoption of an arbitrary already-installed MSI, preserving product code/state and patch history | **needs something else** | The published migration guides cover ClickOnce and Squirrel, not a general MSI-to-Velopack takeover. Assume explicit detection, uninstall/side-by-side policy, data preservation, and enterprise coordination must be designed and verified. |
| macOS .app, ZIP/DMG or package delivery | **Velopack does it** for packaging | Distribution still needs a Developer ID signing and notarization path. Velopack documents sandboxing as unsupported. |
| Linux AppImage delivery and replacement | **Velopack does it** for packaging | The documented Linux output is AppImage, not .deb or Flatpak. It does not replace the existing FieldWorks package ecosystem. |

Velopack’s Windows default is per-user and replaces the current app folder during updates; its optional MSI mode supports per-machine installation, but offers a lighter installer surface than a fully custom WiX product ([Windows packaging](https://docs.velopack.io/packaging/operating-systems/windows), [installer options](https://docs.velopack.io/packaging/installer)). Hooks have no UI or cancellation path and have short time limits ([hooks](https://docs.velopack.io/integrating/hooks)). On macOS, Velopack can produce an app and package/archive forms, but signing and notarization are required ([macOS packaging](https://docs.velopack.io/packaging/operating-systems/macos)). Its Linux output is AppImage ([Linux packaging](https://docs.velopack.io/packaging/operating-systems/linux)). The documented migration list is limited to ClickOnce and Squirrel ([migration guides](https://docs.velopack.io/category/migrating)).

## Motif recommendations

1. **Use a stable Motif package identity and private install root.** Prefer Velopack’s per-user Windows install for a developer-oriented command line. If FieldWorks deployment requires all-users installation, evaluate the optional per-machine MSI as a separate deployment mode. Keep Motif’s app, its ICU binaries, ICU data, and worker beside its launcher. Do not add Motif to machine PATH or reuse FieldWorks’ ProgramData tree.

2. **Give FieldWorks an explicit discovery contract.** FieldWorks should locate Motif via a configured executable path or a small, versioned user/machine registration that can distinguish user and machine installs. Search a known user install first, then a machine install if applicable. Do not depend on PATH: FieldWorks currently edits machine PATH, and multiple Motif versions or accounts make PATH ambiguous. Keep the integration boundary at the CLI: release the FieldWorks project, call motif apply --all-pending, then reload it, as specified by the repo’s FieldWorks integration contract. Avoid coupling Motif’s installer to FieldWorks MSI product codes.

3. **Keep ICU private to Motif’s process tree.** Bundle or otherwise provision the ICU runtime/data for each supported OS, then set any ICU environment variable only for Motif and its child processes. Do not change FieldWorks’ global ICU_DATA, shared Icu70 data, or ICU54DataDir. Resolve the apparent Icu54/Icu70 split with FieldWorks owners before defining any shared dependency.

4. **Treat Windows signing reuse as a question to settle early.** FieldWorks and FwLite visibly use SIL Trusted Signing through TRUSTED_SIGNING_CREDENTIALS, but the sources do not establish that the secret is available to Motif’s release workflow or that Velopack’s pack-time signer can use the same action/profile. Verify account ownership, workflow access, signer invocation, and whether the Velopack-generated setup/update binaries are signed. For macOS, budget for a distinct Apple Developer ID and notarization setup unless an owner confirms existing organization-wide infrastructure.

5. **Keep installer and application lifecycle separate.** Let Velopack own Motif’s files and updates. Let FieldWorks own project loading, releasing, applying, and reloading. Avoid hooks for project changes, user interaction, or machine setup.

## Ranked gotchas and questions

1. **Arbitrary MSI migration is the largest transition risk.** What is the supported upgrade route for existing FieldWorks/Motif-adjacent MSI users: leave FieldWorks installed and install Motif independently, uninstall/replace a package, or support side-by-side periods? Which state must survive?
2. **Machine-wide side effects are substantial.** Which consumer still requires FieldWorks on PATH, FIELDWORKSDIR, global ICU state, the fonts, TECkit/Encoding Converters, registry values, file associations, and silfw:? Can the Motif integration avoid all of them?
3. **The ICU contract is unclear.** Why does ICU54DataDir point at Icu54 while ICU_DATA points at Icu70? What ICU versions and data paths are supported for each current FieldWorks line, and may Motif distribute its own ICU independently?
4. **Enterprise deployment may need a machine install.** Do institutions require Program Files, GPO/MSI deployment, offline installation, or centrally managed updates for Motif? If yes, does Velopack’s optional MSI meet the requirements without FieldWorks-style shared system mutations?
5. **Signing ownership is not established.** Who owns the SIL Trusted Signing profile and can authorize a Motif workflow? Can the Velopack pack operation call the approved signer? Does SIL have an Apple Developer ID team and notarization credentials available for Motif?
6. **Linux FieldWorks guidance may be stale.** Is the FieldWorks 9.0 Flatpak still supported for users when Flathub marks its package EOL? Which ICU package/source does it use?
7. **The installer helper revision must be reproducible.** Should release workflows pin genericinstaller by commit instead of defaulting installer_ref to master?
8. **The build number still reflects a legacy system.** Is Jenkins still producing any installer builds, or is the +1000 offset now only historical compatibility?
