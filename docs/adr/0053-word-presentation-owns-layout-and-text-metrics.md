# ADR 0053: Word presentation owns layout and text metrics

Words and their analyses should remain readable and behave the same wherever a linguist encounters them in Motif. Put their display and interaction rules in one module so a layout correction reaches every list and Text without each page learning how to arrange a word.

Status: accepted for implementation. The design is finalized after the integrator's decision and research lane ln-perf-r5; this document changes no shipping control.

Choose a shallower templated row whose list owns the column schema and width policy. Keep the constrained `ListBox` and `VirtualizingStackPanel`, native selectable text, checkboxes, buttons and named marks. Draw only decorative separators, gutters, underlines and small noninteractive marks into one parent. Do not replace the whole row with a canvas or introduce TreeDataGrid. `ControlTheme` supplies locality; fewer realized elements and bounded layout work supply the intended reduction in cost. Preserve the existing virtualization cache setting; tune `CacheLength` only from native traces after simplifying the row.

The template research at source `e0ba525bf0f76e39ca8f1f5f86a9f3fe5952d5f9` found 111 controls at depth 22 in its row fixture. Its fully drawn probe reduced sampled headless viewport-jump p95 from 1,344.2 to 57.2 ms, but omitted essential interaction and accessibility behavior. This supports reducing repeated structure, not a prediction of desktop speed or evidence for removing native text controls. The inspected implementation at `86c8a634cb11ab6a7ba4dda70e4e3b10f0cba1da` also contains the writing-system resolver added after those probes.

## Ownership and interface

A page chooses which facts to show and what its actions mean. The word display handles how those facts fit, how a person reads and copies them, and how keyboard and accessibility tools reach them.

The App's word-presentation module exposes a small family of lookless templated controls: `WordRow`, `WordStripToken`, `WordCard`, and `WordRowHeader`, each with a local `ControlTheme`. Shared morphology and mark rendering are private to this module unless independently used elsewhere. Preserve `CopyableTextBlock` for selectable text, separate tagged form/gloss/category constituents, checkboxes and buttons for behavior, and named Opinion/outcome/warning/Read controls where they own names, tips or actions. One parent may paint redundant decoration, but never absorbs these behavioral targets. Its depth comes from the behavior behind its interface, not the number of files in its implementation.

Callers supply typed presentation data, a list-owned layout, identity, and typed action requests. Data includes individually tagged linguistic strings, already-derived FieldWorks Opinion and PanGloss outcome, Read state, pending changes, warnings, available analysis evidence, and optional list notes/time values. Existing semantic projections retain responsibility for comparison and meaning. Presentation neither recomputes parser agreement nor persists a mark, stages an Opinion or starts an Assessment by itself.

Open and checked state bind to the host's keyed state; pointer hover, focus and text selection remain local. List selection belongs to the `ListBox` adapter and is distinct from the action checkbox. On recycling, all local interaction state, subscriptions and card work are detached from the old identity. Host actions receive the stable word/occurrence identity and evidence identity, never a visual descendant or concrete host view-model type. Async completions for a replaced identity cannot update the new row.

There are no caller-authored row/card templates, raw `object` action slots, part names, selector classes, per-row column widths, line-height adjustments or ancestor walks in this interface. Variable card contents are typed sections: analyses, warnings, timing, occurrences, comparison alignment, and pending-change context/actions. Real host adapters are needed for Text occurrences, aggregate words and pending changes; a new generic registry of renderers is unnecessary.

## List layout and overflow

Columns stay aligned while a person scrolls, even when newly encountered words are unusually long. Long analyses remain available without putting two independent scrolling surfaces into every word row.

A list creates one column policy and publishes an immutable resolved layout to its header and realized rows. Compute tracks once for each distinct available-width/schema/style/locale input; reuse the result across rows and scroll steps. Preserve existing column order and page column sets, including list-wide hiding of a common Meaning. Use one shell Grid and at most one frame/focus Border; remove the nested grids and redundant edges around the shell. Track topology belongs to the list's schema. Row code-behind never clears/rebuilds `ColumnDefinitions`, binds track minimums to cell desired size, or writes a `SharedSizeGroup`; rendering a different word does not redefine a schema.

Word/mark/number columns use bounded token-defined tracks and measured headings; enabled morphology columns share remaining width. A narrow layout can move the existing next steps below the data. It must not abbreviate FieldWorks or PanGloss or silently hide a requested semantic column. Below the supported minimum, the list may own one horizontal viewport. Zoom changes the root layout transform once; column resolution uses the resulting available logical width.

Compact morphology is a clipped preview with an accessible overflow action opening the full card, replacing per-row `ScrollViewer`s. Full morphology in the card wraps and preserves constituent links, selection and copy; large collections use explicit progressive pages or a bounded detail viewport. Overflow and clipping never imply missing evidence. Replace the scrollbar-specific assertions in `WordRowOpenLayoutSystemTests` with tests proving that every constituent is reachable and copyable. Keep the detailed card's labels, grouping and controls; first optimize repeated rows and strips, and reduce card grouping only if a native trace identifies it as expensive.

Closed rows instantiate no card controls and request no card evidence. Opening requests evidence once for the current identity/revision, with visible loading and failure states; closing detaches card visuals and cancels cancellable work. The host may retain already-loaded evidence separately. Hidden semantic cells are absent, rather than built and hidden. Next-step buttons remain keyboard-reachable and keep their current reveal behavior; their appearance may change row height but cannot change column widths.

## Preventing layout feedback

Opening a word must settle at one width instead of making the window continually rearrange itself. Give the list a stable amount of space and keep every row from changing the rules that determine that space.

The integrator reports a persistent Windows `Infinite layout loop` in `WordRowOpenLayoutSystemTests`: a Grid under `TextWordsPanel` alternates between 714 and 762 pixels. Settings diagnostics also identify automatic scrollbar gutters and zoom as inputs to a width → wrapping/height → scrollbar → width cycle. Per-row column rebuilding and shared minimums supply additional child-to-parent feedback. These are observed failure inputs, not a claim that this documentation lane reproduced the Windows failure or proved it has only one cause.

The list layout owner takes its finite width from the enclosing constrained slot, with a permanently reserved vertical scrollbar gutter in the list theme. Retain Settings' reserved sidebar gutter too. Subtract the same chrome/gaps once for both header and rows. At supported widths disable the list's automatic horizontal scrollbar; compact cells clip/offer overflow and report no desired width beyond their assigned tracks. Any below-minimum horizontal mode is chosen from outer available width and the fixed schema minimum, never a newly opened row's extent. Opening cards, hover actions and arriving data can change height but cannot change the gutter or schema.

The layout dependency is one-way: outer constraint → resolved list tracks → row/cell arrangement → row height. A schema change creates tracks before measuring rows, and a width revision updates only numeric assigned widths once. The list owner can resolve its finite parent constraint at the start of its own measure, before measuring any row; row measure/arrange consume the resulting layout without callbacks that rewrite columns. Identical policy inputs publish no revision and cause no invalidation. Line metrics are a function of text/style and assigned width; a width change may require new wrapping metrics, but the metrics do not feed track widths. Do not move the old feedback into a list-level `LayoutUpdated` loop or fix it with an iteration allowance.

Regression gates observe actual root measure/arrange counts and layout warnings at 1040/1240 window widths, 100/125/150% root zoom, both themes, long/combining/RTL text, opening/closing cards, action reveal, filter/scroll/recycle and scrollbar thresholds. After a genuine resize, the owner publishes at most one layout per distinct input; after settling, repeated layout with unchanged inputs publishes zero layouts and performs zero column mutations. Require zero `Layout cycle detected` warnings and a final successful Windows result; WSL settlement does not prove Windows scrollbar behavior.

## Text style and line metrics

Language text keeps the fonts and sizes the project requests in FieldWorks. Window labels use the bundled interface font and its language fallback, with enough room for actual glyphs and descenders.

One App text-style module resolves a text role, writing-system id, exact FieldWorks style name, UI locale and weight/emphasis against the current captured display inventory and UI font policy. It returns font family/fallback, features, direction, size in device-independent units, and line metrics. One explicit presentation run goes through this seam; native selectable text and editor adapters and the word controls consume the same result.

[ADR 0051](0051-writing-system-display-follows-fieldworks.md) and the [writing-system display contract](../writing-system-display-contract.md) remain authoritative. The App consumes their records, never rereads LDML or reconstructs stylesheet inheritance. Linguistic sizes convert points by `96 / 72`, without clamping or rescaling. Only valid OpenType features render; stored feature strings remain verbatim. Untagged or composed strings do not acquire an invented vernacular id. Each tagged constituent retains its own direction; UI labels follow the UI locale. Running Text order follows its writing system, independently of window direction.

Reuse the ui-font lane's bundled Andika, language fallback map and font collection. UI font initialization and the four Semi/application resource keys have one owner inside this module. Andika is not prepended to a project's requested linguistic family. Locale or Baseline changes publish a new style revision; subscribed text adapters update and detach on disposal.

Line boxes use the actual shaped runs, including fallback glyphs and combining marks. Reuse the text adapter's rendering layout for metrics rather than shaping the same text again through a parallel measurement path. Allocate ascent, descent and leading without reducing a requested font size. A shared form/gloss/category track takes the maximum required metrics of its visible runs. This is local to one row/card or Text line; it never makes every row in a list adopt the tallest word. `RunningTextPanel` consumes explicit line metrics rather than searching classes in descendants and measuring twice to repair gutter heights.

Missing-font notices register when an explicit text adapter first draws nonempty text in a visible top-level surface; publish notices outside rendering. Only those adapters participate in presentation lifecycle. No class handler on every `Control.IsVisible`, window-wide subtree scan or process-static control registry remains. Notice identity is scoped to project display revision and writing system; hide/show and recycling cannot duplicate it.

## Tokens and verification

Theme changes continue to update colors immediately, and zoom continues to enlarge the whole window. Tests check the amount of repeated display work as well as whether words remain usable.

Keep the Primitive → Intent → Component token rules and zero-tolerance gate. Theme-sensitive brushes, shadows and theme objects remain dynamic; invariant spacing, sizes, strokes, radii and UI type sizes use static resources. Writing-system font sizes and line metrics are resolved data, not static UI tokens. Component keys describe genuine reusable controls; page chrome uses shared Intent meanings and page selectors. Move repeated-item selectors into their control's theme for locality, without claiming `ControlTheme` itself improves speed.

Provide read-only diagnostic snapshots through the word-presentation interface: realized visual/control/panel counts, maximum depth, card/cell realization, root measure/arrange invocations and column mutations, plus list schema fingerprint, reserved chrome and layout revision/recomputation count. Tree census is requested after layout, never on each render or scroll. Counters measure actual work, including retired/recycled rows in an observation interval; they do not increment once per requested action as a substitute for measuring layout.

Count roots and all Avalonia/Semi template descendants, including hidden-but-instantiated controls. Report Motif-owned counts separately; exclude only enclosing list/window chrome. Count a card separately and also report the inclusive open-row total. Begin by reproducing the research fixtures: row 111 controls/depth 22, minimal card 63 total visuals/depth 18. Card research also reported 55 descendants; reproduce its category definitions and establish its Control count rather than treating all those figures as equivalent.

Final implementation targets, not measured results: a closed comparison row with three morphemes per producer at most 64 controls/depth 10; a three-morpheme strip token at most 40/depth 9. Retain detailed card grouping with a minimal-card ceiling of 64 controls/depth 18, reproducing the research fixture first; reduce this later only with measured justification. Expanded card counts use an explicit additive budget for realized sections/readings/morphemes/actions, rather than a fixed limit on arbitrary linguistic evidence. Functional controls and automation cannot be removed to satisfy a count. Pin fixtures and framework/font versions and ratchet ceilings only after the real implementation passes. Also report shaped-text layouts and automation peers, so fewer Controls cannot hide repeated work.

On a settled constrained list, one viewport-jump step must leave the column layout revision unchanged, trigger zero column recomputations and zero card loads, and cause at most two root measure and two root arrange invocations per affected realized row; an unchanged retained row outside the step has zero root measures. These are proposed deterministic gates requiring a first instrumented run. Timings and native CPU/GC/layout traces remain reported evidence, not tight shared-runner gates. Counts do not prove desktop latency.

Tests cross the same seam as callers: typed data, resolved layout, host actions, diagnostic snapshots, keyboard/pointer events and automation peers. Replace part-name/class/Subtree tests with semantic column geometry and automation patterns. Preserve canonical comparison/projection tests. Delete `TestFontScale` when the ui-font work and explicit production-metric tests replace it; keep deliberate large-font and zoom tests through supported inputs.

## Delivery and trade-offs

Introduce the design in small changes, each with a working caller and visible evidence. Keep current language, marks and actions unless a specific capture difference records the reason for a change.

Use one Luna lane, with one commit and focused validation at each step: reproduce census/diagnostics and the loop regression; extract text resolution; migrate explicit text subscribers/remove the global hook; implement the list schema/width owner; migrate native morphology/marks; build the shallow row/header and interaction seam; migrate the Word list; migrate shared card evidence/lifecycle without flattening useful detail; migrate Matrix/Fix these first/Lists; migrate Review; migrate Analyze strips; migrate Text-line metrics; migrate Timing/What changed/Warnings; remove the old family and unused styles; run the final Release/capture gate and collect native traces. Each caller migration replaces its previous path rather than adding a permanent compatibility layer. Review viewport virtualization and lazy Text reads remain coordinated independent work; this module does not require a new store generation, CLI verb or Released command.

The costly decisions to reverse are list ownership of width, typed evidence/action seams, and separating run metrics from page styling. Keeping `SharedSizeGroup` preserves content-driven widths but couples scrolling to newly realized content. Merely moving the existing template into a `ControlTheme` preserves that coupling and unnecessary controls. TreeDataGrid offers an example of list-owned columns and recycled cells; Motif's modest fixed set of rich columns does not justify replacing its working list or taking a new grid dependency. AvaloniaEdit's drawing is supported by an editor-scale selection/input/clipboard/automation system, not a cheap substitution for a template. A whole-row canvas is rejected for this implementation. A future narrow drawing experiment requires a native trace showing remaining rendering cost and full behavioral parity before revisiting this decision.

No performance gain or visual validation is claimed by this design document. Each production layout/control change must pass the final-source Release `-All` gate with the pinned PanGloss executable and `MOTIF_SCREENSHOTS`, and record source SHA, parser path/version, capture states, skipped categories and Windows-only follow-up under [development workflow](../development-workflow.md). Native Windows and macOS interaction traces are required before reporting the redesign's desktop performance.
