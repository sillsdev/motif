# ADR 0096 — Writing-system changes are Proposal operations, character class first

**In plain terms:** A linguist or an AI assistant can now propose that a character such as the curly quote stops being part of a word, see what that does to the Texts and the parse on a copy, and then apply it, like any other change to the grammar. Before, only a person could add word-forming characters, directly, with no preview.

Status: accepted (2026-11-09). Owner decision for issue 101: the character-class change becomes a Proposal operation with a Dry Run, a Trial and an Apply, rather than a direct human-confirmed command.

Amends [ADR 0016](0016-scratch-cache-copy-not-undo.md), whose statement that a Dry Run depending on writing-system behaviour is not yet supported now has an exception: the operation below and any later writing-system operation (decision 6) are supported. It does not contradict ADR 0016's canonical path (a file copy of the saved project) or its rule that a scratch is discarded, never reverted.

## Context

`project word-forming` (`ProjectWordFormingCommand`) edits the vernacular writing system of an existing project directly. It is human-only, has no Dry Run, Trial or Apply, and can only add characters, so a character cannot be moved back to punctuation. The first user is Cebuano: U+2018 and U+2019 must be punctuation in `ceb.ldml`, so a word such as `‘baba’` splits at the quotes. The owner chose, from the two shapes in issue 101, to make it a Proposal operation whose Trial reads the changed writing system.

## Research

**How FieldWorks decides a character is word-forming.** `CoreWritingSystemDefinition.get_IsWordForming(int)` (liblcm `CoreWritingSystemDefinition.cs:166-172`) returns true when the character is in a private override set, and otherwise asks `TsStringUtils.IsWordForming`, which accepts letters, marks and modifier symbols. The override set is rebuilt from the writing system's `main` character set whenever `CharacterSets` or the `main` set changes (`:54-97`). Nothing makes a character non-word-forming: the only way to make a listed character punctuation is to take it out of `main`, and a character Unicode already calls a letter, mark or modifier stays word-forming whatever the lists say. The Valid Characters model agrees: `ValidCharacters.Load` reads `main` as word-forming and `punctuation` as other (`ValidCharacters.cs:100-104`), `MoveBetweenWordFormingAndOther` moves a character between them, and `CanBeWordFormingOverride` admits only a single symbol or punctuation character, ZWJ or ZWNJ (`:204-208`, `:279-291`). `SaveTo` drops a set that becomes empty (`:460-475`).

**How LDML stores it.** libpalaso `LdmlDataMapper` writes `main` as `<exemplarCharacters>` with no `type` attribute and `punctuation` as `<exemplarCharacters type="punctuation">`, both in the standard LDML `characters` element (`LdmlDataMapper.cs:1119-1134`); only unrecognised set types go to `sil:exemplarCharacters`. Explicit punctuation therefore needs no `sil:` extension: it is the `punctuation` exemplar set. Absent from `main`, a character is punctuation by default; listing it in `punctuation` records the decision and keeps it a valid character.

**Why scratch copies lose writing-system state.** Three causes, two already recorded and one new.
1. A `kMemoryOnly` copy (`CreateCacheCopy`) re-synthesises writing systems from the bare tag; measured 0 of 4 value-equal (ADR 0016). It stays non-canonical.
2. A file copy is faithful only to what is saved, and a writing system is saved apart from the project. It lives in the project's `WritingSystemStore`, outside the `.fwdata` file and outside the LibLCM unit of work. `FwDataProjectLoader.Save` committed the backend and waited for the write, but never saved the writing-system manager, so a changed writing system reached neither a file copy, a Trial's exported candidate nor a reload. Pinned by `AWritingSystemChangeReachesTheStoreWhenTheProjectIsSaved`, which fails without the fix.
3. Disposing any `LcmCache` saves its changed writing systems (liblcm `LcmCacheIDisposableInterfaceImpl.cs:122`). A scratch opened in place on a published Baseline (`BaselineScratchFactory.OpenSingleUse`) would therefore rewrite the immutable Baseline's LDML after a Dry Run that changes a writing system. Pinned by `AScratchOpenedInPlaceOnAPublishedBaselineLeavesItsWritingSystemStoreUnwritten`, which failed before the fix.

## Decision

1. **Scope.** One operation family, `writingSystems/langProject/…`, whose first kind is `writingSystems/langProject/setCharacterClass`. It moves named characters of one project writing system between word-forming and punctuation, in both directions. No other writing-system field is in scope; collation, fonts, keyboards and valid-character sets beyond these two are not touched.
2. **Shape.** Target is the project root. The closed `after` payload is `{ "ws": tag, "class": "wordForming"|"punctuation", "characters": [one character, …] }`. Each character is one visible code point; whitespace and control characters are refused. The writing system must be one of the project's. The slot is `(project, writingSystems/langProject/characterClass, "<ws>/U+XXXX")`, one per character, so two operations on different characters of one writing system do not conflict and two on the same character do (rule 5).
3. **Semantics.** `wordForming` adds each character to `main` and removes it from `punctuation`. `punctuation` removes it from `main` and adds it to `punctuation`. An emptied set is removed. `punctuation` for a character Unicode calls a letter, mark or modifier is refused, at compose time and again at apply, because no LDML can make it so.
4. **Effect and footprint.** The effect field is `writingSystems/langProject/characterClass`; before and after are `{ ws: "U+2018=<class>/<listing> …" }` where `<class>` is what `get_IsWordForming` answers after the write and `<listing>` is `main`, `punctuation`, `main+punctuation` or `unlisted`. It is read back from the writing system, not replayed (ADR 0006). The footprint digest binds the before text, so a Proposal composed against a different writing system drifts and Apply refuses.
5. **Re-tokenising Texts.** FieldWorks segments a paragraph when it is parsed, and stores the result as the paragraph's segments and wordforms. The operation therefore force-parses (`ParagraphParser.ForceParse`) every paragraph written in the changed writing system that contains a changed character, inside the same unit of work, on the scratch and on the live project alike, so a Trial and Apply see the same Texts. Wordforms the old tokenisation created and nothing now references are left in place, as FieldWorks leaves them; a Trial scope that lists every wordform still lists them, and a caller wanting only the new words names them with `--words`.
6. **Adding fields later.** A further writing-system field is a sibling kind in the same family with the same target, the same `ws` discriminator in its slot and its own effect field. Nothing in the character-class kind is shared by name except `WritingSystemCharacterSets` for the two exemplar sets.
7. **Dry Run and Trial.** Unchanged pipeline. The Dry Run runs on a file copy of the saved project; the operation mutates the copy's writing system and reads it back. A Trial saves its scratch through `FwDataProjectLoader.Save`, which now saves the writing-system manager first, so the exported candidate carries the changed LDML and the re-parsed Texts. `DryRunScratch.Dispose` now forgets unsaved writing-system changes before disposing the cache, so a scratch can never write to the store it was opened on.
8. **Apply.** `ProposalApplier.Apply` mutates the live cache's writing system inside the Proposal's unit of work. The host then calls `FwDataProjectLoader.Save`, which writes the changed definition to the project's `WritingSystemStore` (the LDML) before committing the backend. A writing system is outside the unit of work, so a failed Apply is recovered, as ADR 0016 already requires, by reloading the project, which discards the in-memory definition because nothing saved it.
9. **Recording.** The Proposal records the change as its operation (`kind`, `target`, `after`, `rationale`) like any other, and the Applied Log records the effect. No second store holds writing-system state.
10. **`project word-forming` stays.** It remains the direct, human-only way to declare word-forming characters when a project is first set up and no Proposal or Trial is wanted; it now saves through the same `FwDataProjectLoader.Save`. A Proposal is the way to do it with evidence, and the only way to move a character back to punctuation.
11. **CLI.** `compose-set-character-class` stages the operation in a Draft; the existing `proposal`, `dry-run`, `trial` and `apply` verbs do the rest. It is an advanced AI Draft tool (`motif_set_character_class`).

## Consequences

- The Cebuano change is a reviewed Proposal: the Dry Run shows the two characters change class, the Trial shows how Text Coverage, warnings and parser work move once `‘baba’` is `baba`, and Apply writes the LDML.
- Any other code that saves through `FwDataProjectLoader.Save` now also saves changed writing systems; it writes only the writing systems that changed.
- A character Unicode calls a letter cannot be made punctuation; the refusal says so.
- Re-parsing a large project's affected paragraphs at Apply costs one pass over the paragraphs that contain a changed character.

## Not decided here

Deleting wordforms the new tokenisation orphans; a writing-system operation for fonts, collation or keyboards; moving `project word-forming` onto the operation.
