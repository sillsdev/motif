# Import an edited record file

`motif import --project <fwdata> --file <path> [--draft <name> [--strict]] [--page <n>] [--json]` plans a record file you edited against the saved project, then lowers each change to an operation. Only a person can Apply.

Without `--draft` it is a dry run: it prints the changes (field, old value, new value), the operations they would become and the changes it declines, and writes nothing. The dry run tries the operations on a scratch copy of the project, as staging does, so a change the Runner would refuse is listed as a refusal here and is not staged. With `--draft <name>` it stages the operations in a new Draft of that name and stops there; a name already taken is refused with `draft.name-collision`. A staged Draft holds only the changes that were not refused; the count of refused changes is in the response and in the Proposal's `recordImportRefused`. `--strict` needs `--draft` and without it is a usage error (`record-import.strict-needs-draft` over MCP). With `--strict`, any refused change refuses the stage instead (`record-import.strict-refused`) and no Draft is made. Staging plans the file again against the project and refuses with `record-import.changed-since-preview` if the operations are no longer the ones previewed. A stage that fails leaves no Draft, so the name can be used again. If the file lowers to no operation, no Draft is made and the refusal is `record-import.nothing-to-stage`.

A file made from another schema (for example, a custom field was added after the export) is refused whole as `record-import.plan-refused` with the finding `fwmd.record.schema-mismatch`. A file made from an older state of the record is refused whole: `record-import.plan-refused`, with the base verdict (`stale` or `missing`) in its facts. Export the record again and redo the edits; there is no merge. A file whose `base:` comes from a record the project no longer has is `record-import.record-gone`. A file that cannot be read is `record-import.file-unreadable`.

Creating a record: a file with no `base:` and a `guid:` the project does not have is planned as a create (base verdict `new`). A new main entry or variant entry is turned into operations through the same composers FieldWorks' entry dialogs map to, so it needs what FieldWorks needs: a lexeme form with a morph type and a form text; and either a sense with a gloss and a `morpho-syntax-analysis` that points at one of the file's own analyses (which has a category), or, for a variant, exactly one variant `entry-refs` item with a variant type and one component. Anything else is refused whole as `record-import.create-shape`, naming what is missing, and no Draft is made. A computed field such as `head-word` is `record-import.create-computed-field`. Motif never creates list items: a type, category or morph type must already exist. A new entry can renumber the homograph numbers of existing entries; the dry run of the Draft reports the numbers it changes. A new notebook record is made as FieldWorks' Insert Record dialog makes one: it needs a `title` in an analysis writing system, and its `type` is Observation when the file gives none; setting `MotifJudgmentId` or `MotifJudgmentData` is `record-import.create-reserved-field`. A sub-record added in its parent's file is an edit of the parent, not a create. A complex form, a list item and a phonological rule are `record-import.create-kind-not-creatable`, and a create given as a partial file is `record-import.create-partial`. The GUID must be version 4, 5 or 7 (`record-import.guid-invalid`). With `--draft`, a GUID that another open Draft or Proposal already names is `record-import.guid-pending`; if the other Drafts cannot be read to check, it is `record-import.guid-pending-unchecked` and nothing is staged. A GUID the project's home shows as deleted is `record-import.guid-retired` (not yet reachable from this command). A file with no `base:` that matches the project's record exactly reads as `unchanged`.

Each change that has no operation is listed with its code: `record-import.change-refused` (the importer declines it), `record-import.field-uncovered` (no operation kind writes this field), `record-import.shape-unsupported`, `record-import.value-stale` (the project's value is no longer the one the file started from), `record-import.not-executable`, or one of `fs-notation.syntax`, `fs-notation.unknown-feature`, `fs-notation.unknown-value`, `fs-notation.ambiguous-label`, `fs-notation.repeated-feature`, `fs-notation.unsupported-feature` and `fs-notation.unrenderable` (a feature-structure text that cannot be read or written), `rule-notation.read-only` (rule-formula text an import does not write: a metathesis rule's formula or an alpha variable), `rule-notation.unrenderable` (a rule-formula field the text cannot show), or one of `rule-notation.syntax`, `rule-notation.bad-repeat`, `rule-notation.unknown-phoneme`, `rule-notation.unknown-natural-class`, `rule-notation.ambiguous-label`, `rule-notation.alpha-mismatch`, `rule-notation.index-out-of-range`, `rule-notation.dangling-index`, `rule-notation.context-not-allowed`, `rule-notation.limit-exceeded` and `rule-notation.unsupported-class` (an affix input or output text that cannot be read or written), or `rule-notation.shared-class` and `rule-notation.context-has-data` (a phonological rule's contexts that the text cannot change without touching another object or losing a name or description).

The summary stays within 2 KB. Changes, operations and refusals are listed three to a page; `--page <n>` reads the next page. `--json` and the MCP tool `motif_import_record` return the same `RecordImportResponse`.

Each listed change has a `status` (`staged` or `refused`, with the refusal code). Its old and new values are the file's text, not the operation's value, and they are project text.
